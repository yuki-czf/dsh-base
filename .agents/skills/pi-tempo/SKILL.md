# pi-tempo：DSH 桌面端执行节奏纪律

**一句话**：时间 ≈ 模型往返次数 × 每次等待（PI-Desktop 实测每次往返中位 **7.2 秒**，而工具自身中位只有 **3.6 秒**；DSH 同为 LLM 网关架构，结论可迁移）。
所以整套纪律的主线只有一条——**压掉白往返**。

**实测基线**（PI-Desktop，47 个 gemini-3.8-flash 会话 / 128 个回合，2026-10-16，DSH 待自建基线）：

| 现象 | 基线数据 |
|---|---|
| Edit 调用失败率 | 12.6%（145/1153），其中 110 次是 `EDIT_PARSE_FAILED`（PUT 语法写错）——DSH 的 edit 是字面量替换，此类语法错不复存在，对应失败模式变为「old_string 与现文不匹配」 |
| Bash 调用失败率 | 39.4%（826/2094），其中 stderr 噪声误判 221、60s 超时 58 |
| 重复读 | 单次节点执行 154 次 Read 只对应 38 个文件（**83% 重复读**） |
| 重复验证 | 同一 spec 文件重跑 13 次、`npx vue-tsc -b` 12 次 |
| 单次节点执行 | 307 次往返 = 68 分钟，其中等待占 67%；平均完成回合墙钟 923 秒 |

守下面十条。**这是默认行为，不要等用户提醒。**

## 1. DSH 写工具契约：edit 是字面量替换，write 是整文件

- `edit` ＝ 精确**字面量**替换：`old_string` 必须与文件当前内容逐字符一致（含缩进、换行、标点）；匹配多处会失败，刻意全替才用 `replace_all: true`。**没有 PUT/CUT 行语法，没有行号，没有 tag。**
- **编辑前必须读过文件**（文件观察政策硬性要求：本会话没读过的文件不能直接 edit/write；本会话刚创建或刚改过的除外）。
- **DSH 无「写入后 tag 失效」问题**：写入成功不会让文件变「脏」，`EDIT_TAG_MISMATCH` / `EDIT_LINES_UNSEEN` 这类错误码在 DSH 不存在。
- **批量编辑同一文件的多处改动，一次往返写完**（实测根因：PI-Desktop 上「改一处→重读拿 tag→再改一处」每轮两趟往返约 15 秒；DSH 没有 tag 税，但一趟一趟改依然是白往返）：
  1. **同一批消息里发多个 edit 调用**（多处互不重叠的字面量替换合并一批）；
  2. **`ops_replace`**：一条命令做确定性替换，支持 glob 覆盖多文件（批量机械替换首选）；
  3. **`write` 整文件重写**：大范围改写直接整文件，别硬凑多处 edit。
- **先侦察后落笔**：先把该文件**所有**要改的位置一次看完记下，再一次写掉；**不要**边看边改——每改一次，后续 edit 的 old_string 都要按新内容写，边看边改＝反复返工。
- **唯一等效的「失效」陷阱**：文件被**别处**（另一支 subagent、用户、其他进程）改过 → 你手里的 old_string 已过时、edit 报「找不到」。这不是重读税，是 §9 并行纪律要防的写冲突。
- 真正需要重读的只有两种：① 文件被别处改过（edit 失败且非笔误）② 要改的段落内容确实没读过。

## 2. pwsh 超时与范围

- **先侦察后落笔（顺序别反）**：先把该文件所有要改的位置一次看完记下，再一次多调用写掉；不要读一处→改一处→再找下一处。
- 预计超过默认时长的命令**显式传 `timeoutMs`（毫秒）**，或拆成小步；到时命令会转后台作业，用 `job_output` 收结果、`job_kill` 停止——**超时不是失败**，是转后台。
- 禁止全盘/全用户递归扫描；先限定目录，`ops_glob`/`ops_grep` 天然不穿隐藏与依赖目录。
- PI-Desktop 的「Start-Process 派生进程被 Job Object 回收」问题在 DSH 未复现（每次 pwsh 调用都是独立新进程）；需要常驻进程照常用 `Start-Process`，需要长命令后台化优先用工具自带的 `run_in_background`。

## 3. 判成功看 `[exit code: N]`，不看 stderr 有没有字

DSH 的命令输出以 `[exit code: N]` 标注退出码（exit 0 时常省略标注）。
`npm warn` / `pnpm warn` / `DeprecationWarning` / `browserslist` 会写 stderr 但**退出码为 0**。
不要因此判定失败、重跑或改代码。先看 `[exit code: N]`，再看 stdout 里的测试结论。

## 4. 临时脚本先过语法

写完临时脚本先 `node --check <file>` 再运行（PowerShell 片段先用 `pwsh -NoProfile -Command` 干跑或先 dry-run）；用完删掉。

## 5. 验证节奏：最小子集 → 全量

改一处先跑**单个** spec / 单个测试；全部改完再跑一次全量。
同一套 `vitest` / `vue-tsc -b` 不要反复全量重跑（实测单会话重复 12–13 次）。

## 6. 探索顺序：Grep → 读窗口

`ops_grep` 定位行号 → `ops_inspect_local_file`（或 `read`）带 `offset`/`limit` 读**足够覆盖所需的整段**（一次读够，别 `L1-120`/`L121-240` 分次来）。
路径不确定先 `ops_glob`，**不要猜路径**（实测 25 次 FILE_NOT_FOUND、22 次 Glob 漏 `pattern`）。
**红线**：同一文件在**同一次探索里出现第 2 次小窗口试探**（`limit` ≤ 200 且没命中）→ 停手，改用 `ops_grep` 拿行号。
实测反例：960 行的 `save.ps1` 被以 `limit:120` 读 `offset` 200/500/660/780 四次——既没读到要的部分，又白花 4 趟往返（≈19s）。
**大文件一次读够**：≥500 行的文件，第一次读就把**全部待改区段**一次读进来，不要每处一小窗。实测反例：2000+ 行的页面文件被小窗咬了 8 口，每口多排一趟队、多塞一份进上下文。

**重复读是最大的隐性开销**：实测一次节点执行 **154 次 Read 只对应 38 个文件**——83% 是重复读，
大头是「改完又读」「过一会儿再读下一段」。读之前先问：**我已经掌握的信息够不够判断/下笔？**
够就直接干，不要用「再读一遍确认」当保险（那是 7.2 秒一趟）。真正需要重读的只有两种：
① 文件被别处改过 ② 要改的段落内容确实没看过。

## 7. 工具参数必填项

- `ops_glob` 必须有 `pattern`；`ops_grep` 的 `path` 必须真实存在
- DSH 工具面**常驻**，没有「先 ToolSearch 激活」步骤；`todo_write` 是**整表替换**语义——每次给完整清单，别只发增量

## 8. 往返预算：延迟在模型，不在工具

同一会话实测（gemini-3.8-flash，2026-10-16）：**每次模型往返的中位等待 6.5 秒**（首字 ≈3.8s），
而**工具自身中位耗时 9 毫秒** —— 多一次往返就多 ≈6 秒，与工具快慢无关。

按收益排序的做法：

- **读档 / 检索一次并发**：CONTEXT + PROGRESS + 计划/归档 + DECISIONS 放进同一批工具调用，不要一个接一个来。
- **同一文件一次读够**：见 §6（分窗口读＝白往返）。
- **独立调用同批**：多个读 / 多个搜 / 互不依赖的 pwsh 合并一批；只有有依赖关系的才串行。
- **预告每批一行**：「I will …」不额外增加往返（实测预告→工具发起中位 268ms，属同一响应、约 0.13s/行），但逐工具预告会拉长转录、白耗输出 token；**一批一行**即可。
- **上下文守门**：预判要读 **>30 个文件或 >3000 行**才能动手 → 先派只读 subagent 测绘，主线程只收结论。实测真实节点上下文中位涨到 21 万、峰值 49 万 token——那 47 秒一趟的等待主要就是在重新喂上下文。
- **大输出先瘦身**：跑测试/构建/扫描一律加管道只留结论行（如 `… | Select-String "tests|pass|fail"`），长输出别整段进上下文。**每个工具结果都永久占上下文，白读一次＝给它后面所有趟加重量**——这是自我强化的恶性循环。

## 8.5 锚定（v1.0.2）：用「生成」对抗注意力衰减，被动重读无效

**病根（实测，节点 271）**：开工时 skill 的 6k token 规则占上下文 50% 注意力；跑到中段上下文 33.8 万，它只剩 ~2%——规则确凿在上下文里、确凿没被执行。**被动插入规则副本救不了**：2k token 的副本只会稀释全部注意力（softmax 归一化），模型扫一眼熟悉文本就跳过。

**机制**：注意力按 token 相似度加权。让模型**自己生成**一段与规则语义相关的文本，这些新 token 会在规则与当前任务之间搭桥，把权重拉回去。**关键约束：必须出现在 output 流（助手正文），不许只写在 thinking 里**——thinking 里的 token 不产生恢复效应，实测「在脑子里想过」＝零效果。

**做法（三档）**：

| 档 | 时机 | 形式 | 成本 |
|---|---|---|---|
| **ANCHOR** | 每个批次开工（必做） | 助手正文一行：`ANCHOR: 本批最大风险 → 本批开工前要验证的点 → 适用规则（§号）` | ~20 token |
| MINI | 切分表定稿后 | 正文复述每个批次要守的规则编号与一句理由 | ~120 token |
| FULL | 收口复审简报 | 正文逐条对验收标准，写「怎么验/还没验什么」 | ~300 token |

**强制力措辞**：跳过 ANCHOR 的批次视为**未完成**（后续改动一并无效，需重做）——不是「不推荐」。「不推荐」在注意力衰减后会被忽略，「作废」不会被。实测措辞强度直接决定遵守率。

**失败熔断（v1.0.3，实测 48 次重试换来的）**：同一失败签名（同工具+同命令/同文件+同错误首行）**连续 ≥3 次 → 强制停手分类**，不许直接第 4 次：

| 失败类型 | 判定 | 动作 |
|---|---|---|
| 瞬时故障 | 网络抖动/超时/限流 | 最多再试 1 次，仍败即停 |
| 环境错 | 端口不通/服务没起/localhost≠127.0.0.1/auth 缺失 | **查环境，禁止继续改脚本** |
| 方法死路 | 最小复现也失败/换参数无效 | **换工具**（如 DSH 内置浏览器替代 Playwright）或**跳过并在报告说明**——跳过不是失败，48 次重试才是 |

**批次终止集（开工前声明，随 ANCHOR 一行带出）**：每个批次同时写明上限——`ANCHOR: 风险 → 验证点 → §号 → 本批上限：N 次迭代 / M 分钟`。到达上限未完成 → checkpoint 留断点，报告差距，**不许无声续跑**。

**会话熔断（v1.0.4，线从 50 万下调至 25 万）**：上下文 **>25 万 token** 或进入第 3 个回合 → **不要「继续」**。三方依据合流：本机实测 21 万时规则已衰减（节点 269）＋社区共识 Pro 级 300k 压缩（Gemini 系更弱取下限）＋ Codex 官方自动压缩线 272k。

**到线动作（handoff 优先于 checkpoint）**：先让模型写一句**「新会话接续提示词」**——含当前进度 / 关键决策**及其为什么** / 下一步 / 已踩的坑——新会话粘贴即续。这比裸 checkpoint 可靠：压缩摘要发生在上下文最满＝模型最笨时，而 handoff 是让模型在还清醒时自己精选交接。写完再跑 `save.ps1 checkpoint` 落档案。等效且更快的替代：**换个模型发「继续」**（新视角等效新上下文，实测即此解局）。失败方案不要口头纠偏追加——把教训写进新会话的提示词里重来，失败的中间过程留在上下文里只会加重衰减。

## 9. 多任务切分：并行前先证明「文件集不相交」

并行只在任务真正独立时省时间。划分错了 = 两个 agent 互相作废（后写的会踩掉先写的：字面量 edit 因 old_string 过时失败，write 整文件则直接覆盖先写的改动）。**准确性优先于并行度：拿不准就串行。**

### 判定三步（对每个任务产出「确定 / 推测」两类文件）

1. **枚举文件集**（路径级，不是目录级）。必须来自证据——计划/规格里点名的引用、`ops_grep` 命中、已读的文件；**不许凭命名猜**。已读到的记 `确定`，靠命名或经验猜的记 `推测`。
2. **重叠判定**：
   - 两个任务的 `确定` 集有交集 → **串行**
   - 任一任务带 `推测` 文件、且该文件可能落在共享文件上 → 先 `ops_grep` 确认（把推测变确定）再判；确认不了就 **串行**
   - 全部 `确定`、两两不相交、无接口依赖 → **可并行**
3. **接口依赖**：任务 A 定义的类型/函数/组件被 B 使用 → **契约冻结后可并行**：先写出类型与签名（空实现/骨架）并跑通类型检查，再让 A、B 各自对着冻结契约并行实现；不做冻结就串行。

### 共享文件：只允许一个 owner

下列**类别**天然会被多个任务碰到，判定时一律按「共享」处理：

- **注册 / 入口类**：i18n 注册、路由表、barrel `index.ts`、插件或 DI 清单、API 客户端聚合文件
- **元数据类**：`package.json`、lockfile、`tsconfig`、构建配置、迁移清单
- **共享测试基建**：fixture、helper、全局校验 spec（覆盖率 / 硬编码扫描之类）
- **孪生文件**：同一内容的多个副本（多语言文案、多端配置）——同一 key/条目必须同一个 agent 一起改

做法：**并行任务只动各自的域文件；共享文件由主线程（单一 owner）在并行结果落地后统一收尾。**
这把「共享」从冲突源变成一条串行尾巴，且总量更小。

### 派发与校验

- 一轮 **2–3 个**（每个子代理要付自己的首字延迟 ≈4s）；**只读任务几乎随便并行**（给只读工具面即可），写任务的约束才是瓶颈。给写型子代理**明确授权文件集 + 边界禁区**，它不许碰别的文件。
- **每轮并行落地后做一次越界检查**（这是划分准确性的机器校验，别靠印象）：

  ```powershell
  git status --porcelain      # 或 git diff --name-only
  ```

  只应出现各任务授权集内的文件；出现授权外的文件 = 划分失败，先处理再继续。
- 每批落地跑**该批的最小子集**（相关 spec）；整仓门禁 / 全量测试由主线程在**所有并行批落地之后跑一次**。

### 不并行的情况

- 文件集只能靠推测（无法确认）
- 改动互相耦合：同一行为、同一状态机、同一测试断言
- 任务小到「写简报 + 复核」的成本超过并行收益

### 规模过大就拆批（先于以上所有判定）

并行只能压"等待"，压不掉"工作量"。**开工时先量规模**，超过任一阈值就**拆成 2–3 个子批次**逐批走：

| 信号 | 阈值 |
|---|---|
| 预计实现量 | **> 2000 行** |
| 改动处数 | **> 100 处** |
| 预估时长 | **> 40 分钟** |

拆批做法：按「切分表」的批次分组 → 每批走"实现 → 局部验证 → 暂存" → 批间留断点（节点协议用 `save.ps1 checkpoint`）。

**实测教训**：一次节点执行 = 43 次编辑 + 154 次读 + 307 次模型往返 = **68 分钟**，单会话吃满 57% 上下文。规则只能削掉其中约 15–20% 的浪费（重复读、单点改、假失败），**剩下一半以上是工作量本身**——那只能靠拆批或派子代理。

**派 fixer 的触发条件**（三条必须同时满足）：① 独立文件集（与主线程不相交）；② 主线程手上有别的活；③ 规模够大——该支预计实现 **>2000 行**、或自身 **≥8 个串行往返**（要跑测试→看结果→再修的迭代）。**耦合判据（拆前必查）**：要读 **≥3 个属于其他分支的文件**才能确定接口 → 不拆。**文件多 ≠ 该并行**：实测 21 文件的节点主线程 1 个往返并发写 16 个文件（99.6s）落地，派 3 个 fixer 要 ≈10 个往返。

## 10. 子代理依赖：主线程当调度器，别让子代理互相等

**机制前提**：子代理之间**没有通信通道**——各是独立会话，只有主线程能看到它们的报告。
所以「B 需要 A 的产出」这件事只能在**主线程的调度**里表达；让 B 自己去等或去猜，必然出错。

### 依赖四型 → 处理

| 型 | 特征 | 处理 |
|---|---|---|
| **A 无依赖** | 各自读写不相交的文件 | 同批并行（§9 判定通过即可） |
| **B 接口依赖** | B 用 A 定义的类型/函数/组件 | **冻结契约消解**：主线程先写类型＋签名＋空骨架并跑通类型检查，再同批并行 |
| **C 数据依赖** | B 必须先知道 A 的结论才能动手（例：要改哪些文件） | **真串行，分两批**：A 批（一般只读、低档）→ 主线程汇总并重新切分 → B 批 |
| **D 汇聚 fan-in** | 多支产出需要合并/交叉验证 | 同批并行 → 主线程 fan-in（合并＋越界检查＋单次门禁） |

### 调度动作（DSH 原语）

- **派发**用 `subagent` 工具：**异步**——立即返回 id，完成时会在本会话**主动通知**，无需轮询；**同一条消息里发多个 subagent 调用 ＝ 并行**。
- **收敛**：等完成通知到齐即 fan-in（等效 PI-Desktop 的 `TaskWait mode:all`——**类比而已，DSH 没有 TaskWait 工具**，收敛＝等完成通知本身）；需要批量编排/JSON Schema 校验时用 `workflow` 工具——`parallel()`（全量屏障，等全部）、`pipeline()`（条目间**无屏障**，先完成先进入下一阶段，近似 TaskWait 的 `mode:any`——同样是类比，DSH 无此工具）、`agent(prompt, {schema})`（机器可校验的结构化回报）。DSH 无参数级 `minCompleted` 原语；`mode:any`＋配额语义用 `pipeline()` 近似（若不够，见开放问题：Promise 竞速能否精确实现 mode:any——备查）。
- **等待超时不是失败**——subagent 还在跑，可以先干别的，通知到了再收。
- **派完不空等**：主线程同时做不依赖它们的事（写契约/类型、改自己那份域文件、读档、备下一批简报）。收口复审这类"派完就没活"的场景，**从派发到收到完成通知之间至少塞 2 个往返的活**（写归档正文、生成 CONTEXT 暂存、把收口要用的脚本一次读完）——只做 1 件就等＝白烧整段等待（实测空转 107 秒 ≈ 全程 20%）。可执行清单见各仓 node-run 模板。
- **fan-in 前先做越界检查**（§9）：`git status --porcelain` 只应出现各任务授权集内的文件。
- 每批落地跑**该批的最小子集**；全量门禁只在 fan-in 之后跑一次。

### 该不该引入依赖链（成本口径）

每次「等」的成本 ≈ 主线程一次往返（实测中位 **6.5 s**）＋ 子代理首字（≈**4 s**）＋ 报告往返。
链长 2–3 就把并行收益吃光了，所以：

- **任务小且必须串行 → 主线程自己做**（省掉「写简报 + 读报告」两次往返）。
- **任务大、或必须隔离上下文（大量只读探查会淹掉主上下文）→ 才派子代理**。
- 依赖能被主线程**提前决策**的，就在主线程决策（决策冻结＝B 型的一种），这是把 C 型变成 A 型最常用的手法。

### 接力模式：长节点让子代理扛重活，主线程只当调度器（v1.0.8）

**触发（v1.0.6 改为档案驱动，不再靠现场判断）**：实测 7 个真实节点（268–272＋沙盒×3），执行会话对「要不要派」的**现场判断零触发**——模型永远判「自己几个调用就能干完」（对照证据：同一会话里，程序性步骤——派复审/ANCHOR/存档——执行率接近 100%，判断性步骤全部衰减）。解法不是更响亮的劝说，是**把拆分前移到规划落档**：计划节点行带 `执行:执行接力` ＋ `plans/<名>.md` 七列接力表（批/名称/范围/**执行者**/验收/预估材料K/前置批）。执行会话读到标记 → 照单循环，**没有判断环节**。规模参考：预估 >40 分钟 / >2000 行 / >4 批次。**目的不是并行提速，是上下文保鲜**——与 §9 并行判定无关：那边为速度（短节点主线程自己批量写更快），这边为不衰减（长节点主线程一碰大文件就膨胀）。两套判据并行不悖。

**流程（照单，程序性）**：主线程**不碰源码、不跑测试/门禁**（验证归执行棒与复审棒）。派发后主线程合法动作**仅四类**：①读子代理报告并记 facts ②备下一棒简报 ③存档/SESSIONS 留痕 ④`git status --porcelain` 越界检查——「派完不空等」在接力模式下＝做这四类，**不是自己去写码**（272-R1 实测：主会话越权写码＋自跑门禁＝两轮 3 连败失败循环＋~15 分钟重复劳动）。每棒 ＝ 读棒简报 → `subagent(执行棒简报)`（DSH：providers/model 在调用层传，见 node-run DSH 版）→ 等完成通知收敛 → 报告事实（各段 ≤300 字）追加 `.nodes/relay/<名>/facts.md` → 越界检查（只应出现该棒授权集内文件）→ 下一棒。全棒完成 → 复审棒（independent-review 简报，**换 provider 异构**；**报告须含逐项行号证据，不完整即重派**）→ 存档收口。主线程上下文每棒只涨「简报＋报告」≈3k，十棒也稳在 8 万内。**失败处理**：执行棒报告失败 → 修简报重派；**同棒重派 ≥2 次即熔断**停棒报告用户（失败三分类：瞬时/环境/方法死路）。**拆棒规则（272-R1 实测教训）**：**同一文件的全部条目＝1 棒**（预估 >2 小时才按不重叠区段拆）——按缺陷类别把同一文件切成多棒＝每棒重复付「新鲜上下文重读该文件」的成本（1500 行文件每棒侦察 5–8 分钟，4 棒白付 ~25 分钟），只亏不赚；接力的甜区是**多文件多域**任务。
**并行批与双节点（v1.0.8）**：①**基线快照**——接力开工先 `git status --porcelain > .nodes/relay/<名>/baseline.txt`；越界检查＝「快照后新增且不在本棒授权集」的行（双节点并行时对面节点的合法改动不再误判越界）。②**同批号并行**——接力表「批」列同号＝同批，一次消息并发派发 ≤3 支；并行批按**运行时域**切，同域内「被其他棒 import 的文件＝共享接缝」不可并行——文件集不相交 ≠ 依赖不相交（agent-methodology 规则 4 直译；R2 实测：主会话对 fixer 半成品跑测试即假红）。③**接缝串行棒**——i18n 键/路由注册/门禁白名单/barrel 等共享面由单一串行收尾棒统一处理。④**定向门禁窗口**——任何棒在跑期间，门禁只跑该棒路径域；全仓回归留到全部棒落地后由回验棒跑一次——**信退出码，不信报告**（R2 实测执行自评不可信）。⑤越界改动＝revert 不 merge。⑥**双节点并行**——同仓 ≤2 个接缝不相交的独立节点可同时执行（前提＝基线快照＋定向门禁生效）；>2 个或接缝相交 → 串行；跨仓随意。

**接力简报（六段，缺一不可）**：

```
GOAL: 本批要达成什么（一句话）
验收: 怎么算完成（可判定的）
文件集: 授权改动清单 ＋ 边界禁区（明说不许碰的）
已验证事实: 接口签名/路径/已排除的假设——省它重新侦察（这是 fork 语义的手工替代）
验证: 跑什么命令证明（如 node --test test/x.test.js）
终止: 最多 N 次迭代；验证不通先做最小复现，3 次失败即写报告返回，禁止死磕
```

**回报要求（写进简报末尾）**：改动文件清单＋每处一句话原因＋验证结果原文（pass/fail 行）＋未决风险，**各段 ≤300 字**（防报告回流撑爆主线程——报告是给调度器记账的，不是给主线程重放执行的）。主线程把报告当下一棒的「已验证事实」——这就是 handoff 的自动化版。

**边界**：无明确文件集的探索性批次不接力（授权集写不出来）；短节点别用（每棒多付 2 趟往返）。**修订早前决策**：「明确放弃 Core never writes code 路由器模式」的前提是省贵模型 token；多账号 token 池下动机改为抗长上下文衰减，纯调度模式重新成立——但**仅限档案化接力表驱动的形态**（先落表后执行），不接受执行会话现场自判。
- **执行槽闸（v1.0.9）**：节点登记的验收标准末尾必带 `执行:` 槽（`执行:执行接力` 或 `执行:—(自干理由)`），`save.ps1 next-node` 硬校验；node-run 读档后无执行槽且任务 ≥3 → 停下补登记再开工，不默认自干（#273 实测：无槽自干＝57min／ctx 498k／看门狗六弹）。
- **双轨自检与返工棒（v1.0.10）**：接力每棒收敛先 `git status --porcelain` 对比授权集——授权集外改动＝调度器抢写违规，**停止而非重派**（#274 实测：主会话 78 Edit 与棒赛写→2 次棒重派＋ctx 408.9k，重派救不了双轨）；等待窗口禁读源码本体（读棒报告/facts 即可，274 的 433 次 Read 是烧穿上下文的直接原因）；复审发现问题 → **单支返工棒**吃完所有发现（含验证），主会话禁参与返工；DSH 无会话级只读开关——「物理剥夺写工具」由**预设工具面**承担（如只挂读的 librarian 预设），有条件即用。

### 反模式

- 让 B 先开跑、指望 A 的产出「大概就是这样」→ 必返工，比老实串行更慢。
- 用子代理实现「等待」——子代理没有等待原语，它只会去猜或空转。
- 同一批里让两支碰同一个文件（含共享文件）→ 见 §9。

## 自检

**锚定输出的验收（v1.0.2 起）**：会话转录里每个批次的**助手正文**应出现一行以 `ANCHOR:` 开头的文本（thinking 里的不算）。节点收口时数 `ANCHOR:` 出现次数 ≥ 批次数 − 1 即视为锚定生效；整场 0 次＝纪律未被遵守。

**核心验收口径（v1.0.1 起）＝「每改一处摊几次模型往返」＝ 总往返数 ÷ (edit+write) 次数，达标线 ≤5**；
基线 7.8（无纪律）→ 实测 4.4–4.6。旧口径「每趟 ≥2.5 个调用」只适用于小文件项目——大文件环境下天然达不到，**不作验收用**。
