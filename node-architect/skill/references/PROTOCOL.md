# .nodes 节点协议（客户端无关版）

> node-architect v__VER__ · 本文件是协议规则的**唯一真源**；SKILL.md 与 AGENTS.md 中的条款为摘要，如有分歧以本文件为准。
> 核心理念：**文件是记忆，对话不是**。上下文压缩不可避免，唯一可靠的记忆是磁盘上的档案。

## 目录

```
.nodes/
├── CONTEXT.md    项目一页纸快照（一屏以内）
├── PROGRESS.md   节点矩阵（一行一节点）
├── DECISIONS.md  决策日志（只追加）
├── SESSIONS/     每个会话一个私有状态文件
├── archive/      节点归档与旧决策归档
├── plans/        分批执行约定与各节点批次计划
├── PROTOCOL.md   本文件
└── .lock.d/      写 CONTEXT.md 时的临时锁（目录锁，原子创建）
```

## 开工协议

1. 读 `CONTEXT.md` + `PROGRESS.md`（必要时读 `DECISIONS.md` 最近条目）。
2. 用一两句话向用户复述"当前节点 / 下一步"，确认后再动手。

## 节点协议

- 节点 = 一个可验收的交付物，不是任务清单。边界由 AI 提议、用户确认。
- 新节点开工前：在 `PROGRESS.md` 登记行（名称 / 验收标准 / owner / 状态），敲定设计要点写入 `CONTEXT.md` 的"下一步"。
- 会话内的细粒度步骤用各自客户端的任务清单机制管理，不写入节点档案。
- 状态取值：待开始 / 进行中 / 待验收 / 已完成 / 已归档 / 已废弃

## 执行效率协议（登记时侦察，归档时复盘）

节点耗时的大头往往不是编码本身，而是「执行期才暴露的计划期问题」：测试 mock 缺失导致的批量返工、验证命令逐项跑（每次工具冷启动 10s+）、可并行的批次被串行执行。把这三类问题提前到登记阶段解决：

1. **开工侦察（登记后、写代码前必答；结论落入 `plans/<节点名>.md`，无批次计划的小节点落入 CONTEXT「下一步」；结论同时用 `save checkpoint -Node X -Recon "…"` 登记进 SESSIONS，verify 对缺失者 WARN）**：
   - **测试基建盘点**：目标文件的既有测试如何 mock 依赖？grep 测试文件的 `vi.mock` / `jest.mock` / `vi.hoisted` 得出结论。
   - **新依赖打样**：本节点是否给「测试未 mock 过某依赖」的组件引入该依赖？是 → 先在单个组件打样（含测试绿），再批量铺开，防整批返工。
   - **门禁合并**：本节点全部验证命令合并为批末一条跑；项目侧可提供 gate 聚合脚本，协议不规定具体命令。
2. **批次依赖标注**：多批节点的批次计划「前置批」列如实填写；无共享写点的批次显式标注「可并行」。
3. **批内检查点（未拆批的中型节点必守）**：预估 15~40 分钟、不拆批的节点，每完成一个子块（一个视图 / 一个模块 / 一组同类改动）即跑一次 `save.ps1 checkpoint -Node X -Note "…"` 记轻量检查点（批末再走完整 save）——巨头会话被切成有干净恢复点的段，返工循环最多污染一段，崩溃/压缩随时可续。
4. **效率复盘（归档必填）**：archive 的「执行效率复盘」段填预估 vs 实际耗时、最大浪费点、一条可复用结论（值得沉淀的照常追加 DECISIONS）。`verify -Completed` 机器校验归档无未替换的模板占位符，兜住漏填。
5. **待验收收敛**：`save.ps1 review-audit [-Over 14]` 列出挂账超期的待验收节点（有超期 exit 3）；verify 出现待验收 WARN 时择机跑一次盘点，逐节点「验收 / 废弃 / 登记保留原因」，不让待验收无限堆积。

## 存档协议（触发时机：节点完成 / 用户要求 / 大改动落地 / 会话收尾）

机械动作（锁 / 校验 / 归档骨架）优先交给 skill 的 `save.ps1`（位于 `.agents/skills/node-architect/scripts/`）；无脚本环境时按各步骤括号内的规则手工执行。

**完成字样时序**：verify/verify-batch 清单全 [OK] 之前，任何档案不得写入"已完成"类表述，避免提前宣告完成。

1. `PROGRESS.md`：定向更新该节点行。
2. `SESSIONS/<会话标识>.md`：重写本会话状态。
3. `DECISIONS.md`：有新决策则末尾追加（不改历史）。
4. `CONTEXT.md`：写暂存文件 → 调 `save.ps1 save`（自动 lock→替换→unlock→verify）。
   - 手工等价：建 `.lock.d/` → 写 owner 文件 → 重写 CONTEXT → 删 `.lock.d/`
   - 批次场景改用 `save.ps1 commit`（含 verify-batch）
5. 节点完成：`archive/<节点名>.md` 归档细节（`save.ps1 verify -Completed` 可自动生成骨架）。
6. 收口：`save.ps1 verify` 清单全 [OK] 才算存档完成（手工等价：对照 1-5 逐项自查）。

### 一键存档（save 动作）

非批次场景的常规存档，`save.ps1 save` 单命令完成第 4-6 步：lock → 用暂存文件原子替换 CONTEXT.md → 删暂存 → unlock → verify。正常 exit 0（暂存已删）；锁竞争 exit 1（暂存保留，重试同一命令免重写）。

### 原子收口（commit 动作）

批次场景的批末收口，`save.ps1 commit` 单命令完成：lock → CONTEXT 原子替换 → 删暂存 → unlock → verify-batch。正常 exit 0（暂存已删）；锁竞争 exit 1（暂存保留，重试免重写）；校验 FAIL exit 1（CONTEXT 已落盘无损，按修复提示处理）。`"完成"` 字样只允许在 commit exit 0 之后写入。

## 并发协议（多会话）

- `DECISIONS.md` 只追加；`PROGRESS.md` 只改自己节点的行；`SESSIONS/` 只写自己文件。
- `CONTEXT.md` 写入通过 save/commit 命令自动加锁（目录锁 `.lock.d/`，原子创建；10 分钟超时；超时可覆盖；只能删自己的锁或超时锁）。手工操作须遵守同样规则。
- 冲突时重读合并，不盲目覆盖。

## 体积协议

- **硬上限（v1.7.0 机器闸门）**：`CONTEXT.md` ≤60 行且每行 ≤6000 字符；`PROGRESS.md` 表格行 ≤600 字符；`DECISIONS.md` ≤200 行。超限时 `save`/`commit` 被拦截（exit 4，10 分钟内同命令重跑放行一次）；`verify` 报 FAIL 项。
- 滚出修复：`save.ps1 trim-context`（已完成条目/超长引言 → `archive/context-<日期>.md`）、`trim-progress`（超长行按列预算截断，原文全文 → `archive/progress-rows-<日期>.md`）、`trim-decisions`（行数感知：自动减保留条数保 ≤200 行）。均默认 dry-run，`-Apply` 落盘。
- 常态写法：核心文件只留一句话状态，细节直接写 `archive/<节点>.md`；除超限外闸门全 fail-open。
- **协议本体红线**：`PROTOCOL.md` 自身保持 ≤150 行——超限即把细则下沉 `archive/` 或 skill references，正文只留规则条目。规则墙（过长协议）会被执行会话整段忽略，长即失效。

## 批次协议（单节点超单会话预算时拆批执行）

- **触发条件**：登记节点时预判**超出单会话预算**（上下文预算＝实读材料将超压缩点；或工作量预算＝预估触碰 >15 文件 / >100 处改动 / 预估 >40 分钟——上下文不超但工作量超的「时间巨头」节点同样触发）→ **立节点先问**（询问制）：spec-superflow（proposal/specs/design/tasks + execution-contract 门禁，重型）还是本分批约定（plans/<节点名>.md + 一批一会话，轻量），二选一并向用户说明，**不得混用**；用户选定本约定 → 登记同时在 `.nodes/plans/<节点名>.md` 落批次计划；PROGRESS 状态列记 `进行中·批N/M`。
- **批次计划文件**：`.nodes/plans/<节点名>.md`，模板 = `templates/BATCH-PLAN.md`；核心为六列表：批 / 名称 / 范围（文件/函数）/ 验收标准 / 预估材料K / 前置批。单批输入材料默认 ≤30K tokens，按校准日志调整。

- **执行规则**：
  1. **拆批时机**：登记节点时同步落批次计划文件，不事后补。
  2. **切割原则**：按复杂度切、不按文件大小切——思考密集的步骤单独成批；批间靠文件/接口衔接，不靠会话记忆。
  3. **一批一会话**：每批开新会话，照常走开工协议读档，但只读本批相关档案；会话标识按批轮换 `<节点>-b<N>`，避免 SESSIONS 覆盖上批暂停点。
  4. **批末必存档**：走存档协议（收口固定走 `save.ps1 commit`，禁止手工拆步 lock/unlock）；SESSIONS 暂停点写「已完成批N：<产出>；批N+1 从 <文件/步骤> 开始」，CONTEXT 下一步指向下一批。**完成字样时序**：verify-batch 全 [OK] 前不得在任何档案写入"已完成"表述。
  5. **超限即断**：实读材料超阈值或接近压缩点 → 提前收口存档换会话，不硬撑。
  6. **校准回路**：每批回填计划文件校准日志（格式：预估 X 分钟 / 实际 Y 分钟 / 最大浪费点一句话），verify-batch 机器检查；回头调阈值。
  7. **并行批**：批次计划标注「可并行」且无共享写点的批次可同时执行——每批在计划表声明**独占文件集**，越界改他批文件即违规；有共享写点的批必须串行。载体二选一：① 并行会话（各自五步存档收口；commit 撞 CONTEXT 锁 exit 1 属预期，重试同一命令即可）；② 编排会话内并行子代理（**派发前先 save 中途存档、子代理全部回收后逐批收口 commit**——子代理失败不留断点，靠编排者补）；机械批可指定轻量模型执行。
